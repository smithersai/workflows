# Local Code Review

Review the change that was just implemented in this repository, **locally**. Nothing has been
pushed and there may be no PR — the work is in the working tree in front of you. Read it, judge it,
and report findings. Do NOT fix anything, do NOT commit, do NOT push, do NOT post a comment
anywhere, and NEVER merge. Your only output is the JSON verdict at the end.

## Follow the review contract

If a **`xiv-review-core`** skill is available to you, load it now and follow it — it is the
authority for this review and supersedes the summary below. If you have no such skill, the summary
below IS the contract; follow it as written.

## Gather context first

Before judging the diff:

1. **Read the change.** It is normally uncommitted work on the current branch:

   ```bash
   git status --short                 # includes untracked files — read those too
   git diff HEAD                      # staged + unstaged changes
   git log --oneline -5               # anything already committed on this branch
   ```

   If the branch already has commits, also diff it against its base
   (`git diff $(git merge-base origin/HEAD HEAD) HEAD`). Read the surrounding files for context,
   not just the hunks — a change is only correct relative to the code it lives in.

2. **Check acceptance-criteria parity.** The issue's criteria are in the REQUEST below. A gap
   between a criterion and what was actually implemented is itself a finding, and so is a criterion
   with no meaningful test covering it. "Meaningful" means the test would fail if the behavior
   regressed — not a tautology, not a mock asserting itself.

3. **Reconcile prior review comments, if there is an open PR for this branch.** Check with
   `gh pr view --json number,url` (silently continue if there is none). If one exists, read *every*
   comment surface — formal reviews, inline diff comments, and conversation comments — and verify
   each earlier finding against the **current code** rather than the thread's resolved state.
   Re-flag anything still unaddressed or only partially fixed; don't re-raise what a live comment
   already covers.

4. **Check CI, if the branch is pushed** (`gh pr checks` or `gh run list -b <branch>`). A failing
   build, test, lint, or type check usually points straight at a real finding.

## What counts as a finding

Flag an issue only when all of these hold:

- It meaningfully affects correctness, security, performance, or maintainability — or it is an
  acceptance criterion that is unmet or untested.
- It is discrete and actionable: one specific fix, not a diffuse critique.
- It was introduced by this change. Pre-existing bugs are out of scope.
- The author would fix it once aware, and it is not clearly an intentional choice.
- It holds without unstated assumptions. For cross-file breakage, name the code that is *provably*
  affected — never speculate that something "might" break.
- The rigor of the fix matches the surrounding codebase.

Report every finding that clears that bar — don't stop at the first. If nothing clears it, return
no findings rather than padding the list with weak ones. Ignore trivial style unless it obscures
meaning or breaks a documented standard.

## Writing each finding

- `title`: short and specific. `body`: one paragraph at most — lead with why it is a bug and state
  the conditions (inputs, environment, scenario) it needs. Matter-of-fact tone, no flattery, no
  restating the file location in prose.
- `path` is repo-relative; `line` is the line the finding anchors to (set `startLine` too, but only
  for a real range). Leave them null for a general finding.
- `inlineable` must be **false** here — this review is local, not anchored to a PR diff.
- `severity` is one of `blocker`, `high`, `medium`, `low`, `nit`.
- Give each finding a unique `id` (`f1`, `f2`, …).
- Keep any code fragment to 3 lines or fewer, wrapped in inline code or a fenced block.

## Verdict

- `request_changes` — an unmet acceptance criterion, a criterion with no meaningful test, or any
  `blocker`/`high` correctness or security finding. This sends the work back for another
  implementation pass, so use it only when the change genuinely is not done.
- `comment` — findings worth raising, but nothing that should block. The work proceeds.
- `approve` — every acceptance criterion is met with evidence, covered by meaningful tests, and the
  change is production-ready.

Write a concise `summary` (markdown) explaining the verdict, citing the file, test, or command
output that evidences each criterion you consider met.
